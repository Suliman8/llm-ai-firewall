2 · Life of a single request

Follow one user prompt as it travels through the firewall. Yellow steps are decisions. Red steps mean the request was blocked.

1

User sends a prompt

Example: “Summarise this PDF I uploaded.” Hits the FastAPI gateway endpoint /v1/chat.

2

Rate limit check (Redis)

Has this user sent too many requests in the last minute? If yes → block. If no → continue.

3

Pre-process the input

If the prompt has attachments (PDF, URL), extract their text using PyPDF / a web fetcher. The text now contains both the user’s words and the document text.

4

Layer 1 — XGBoost classifier scores it

Returns a number 0.0 → 1.0. Above 0.9 → clearly malicious, block. Below 0.2 → clearly safe, pass. In between → forward to Layer 2.

if score > 0.9
✕

BLOCKED

Return “Request blocked by AI Firewall (L1)”. Log the attempt.

if uncertain
5

Layer 2 — LLM-as-judge

A second AI reads the prompt and answers: “Is this trying to manipulate the assistant?” If yes → block. If no → continue.

6

Layer 3 — Indirect injection scan

If the prompt has document text attached, scan it for hidden text, white-on-white text, suspicious instructions like “ignore previous”. Block if found.

7

Layer 4 — Inject canary tokens

Add 1–2 fake “secret” strings into the system prompt the AI sees. We will check later if any of these leak into the reply.

8

Forward to backend LLM

The cleaned prompt is sent to OpenAI / Anthropic / self-hosted Llama. Whichever the user requested.

9

Output check — canary leak?

Does the AI’s reply contain any of the canary tokens we planted in step 7? If yes → the AI was tricked. Block the response.

10

Output filter

Strip leftover PII (emails, phone numbers, internal URLs) just to be safe.

11

Send safe reply back to user

Plus emit telemetry: which layers ran, scores, time spent, verdict. Stored via OpenTelemetry for the OWASP report.

3 · Why “layers” — the Swiss-cheese model

No single detector is perfect. Each layer has gaps. But when stacked, the gaps don’t line up — so an attack must beat every layer to succeed. This is the heart of the project.

L1

XGBoost classifier (fast)

Pattern-matches known attack shapes. Cheap. Runs on every request in under 10 ms.

Catches: known jailbreaks, repeat patterns
L2

LLM-as-judge (smart)

A second AI reads borderline prompts and gives a verdict. Slower, but understands meaning.

Catches: paraphrased attacks, novel jailbreaks
L3

Indirect injection scanner

Looks inside uploaded PDFs, web pages, and RAG chunks before the AI ever sees them.

Catches: poisoned documents, hidden text
L4

Canary-token tripwire

Plants fake secrets and watches the output. If they appear in the reply, exfiltration was attempted.

Catches: data theft, system-prompt leak
L5

Rate limiting

Stops one user / one IP from hammering the system to brute-force jailbreaks.

Catches: brute-force probing, abuse
L6

OWASP LLM Top-10 test harness

Not a runtime layer — a CI test that runs every known attack on every code change. Stops regressions.

Catches: regressions, broken defences

4 · Key design decisions (in plain English)

These are the “why” behind the diagrams above.

Why fast L1 before slow L2?
XGBoost is < 10 ms. LLM-judge is 500–2000 ms. Most prompts are obviously fine — we only “pay” for the slow check on the 5% that look uncertain. Saves money and latency.
Why scan documents (L3)?
In RAG apps, the most dangerous attacks come not from the user but from documents the AI loads. The bank PDF story is exactly this. L1 + L2 only see the user’s text — so we need a separate layer for document content.
Why canary tokens (L4)?
No detector can read the AI’s mind. Canary tokens flip the problem: instead of guessing intent, we leave bait. If the AI ever speaks the bait, we know something went wrong — even if we don’t know what.
Why three different LLM backends?
Real production systems are multi-vendor for cost + reliability + privacy. Showing the firewall handles all three (OpenAI, Anthropic, self-hosted Llama) makes the project realistic.
Why Redis instead of Postgres for rate limits?
Rate limiting needs millisecond reads per request. Postgres is too slow for that. Redis is in-memory and gives sub-millisecond reads. We use Postgres only for the slow audit log.
Why a CI test harness (L6)?
The defences mean nothing if they silently break in a code change. The OWASP test harness re-runs every known attack on every commit — like unit tests, but for security. This is what makes the system production-grade.
