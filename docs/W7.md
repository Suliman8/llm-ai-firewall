## 4. Concepts learned

### 🎓 Local LLMs vs cloud LLMs

| | Cloud (OpenAI/Anthropic) | Local (Ollama) |
|---|---|---|
| Cost | $$$ per token | $0 forever |
| Latency | 100–300 ms (network) | depends on CPU/GPU |
| Privacy | Data leaves your machine | Stays on your machine |
| Reliability | Their uptime | Your uptime |
| Offline | ❌ | ✅ |
| Compliance (HIPAA, GDPR) | hard | easy |

For a firewall product this is a real selling point: *"works air-gapped, drop-in for self-hosted teams"*.

---

### 🎓 Why Llama-3.2-3B (and not bigger)

| Model | Size | Speed on CPU | Quality |
|-------|------|--------------|---------|
| **llama3.2:3b** ⭐ | 2 GB | 3–5 s/reply | Decent |
| llama3.1:8b | 5 GB | 10–20 s/reply | Better |
| llama3.1:70b | 40 GB | needs GPU | Excellent |

We just need a **working** local LLM to demo backend integration. Quality isn't the point — the firewall layers are. Switching model is one config change.

### 🎓 OpenAI-compatible API as a lingua-franca

Ollama exposes its API at two URLs:
- `http://localhost:11434/api/...` — native (Ollama-specific)
- `http://localhost:11434/v1/...`  — **OpenAI-compatible**

We use the second so the `openai` Python SDK works unchanged — just point `base_url` at `http://localhost:11434/v1`. **Same code path** as our Groq integration. This is also how the L2 LLM-judge hits Groq.

```python
self.client = AsyncOpenAI(api_key="ollama-no-key", base_url="http://localhost:11434/v1")
```

That's it. The whole "swap in a local LLM" delta is two lines.

### 🎓 Token-bucket rate limiting — the algorithm

Picture a bucket:

```
        ┌───────────────┐
        │ ●  ●  ●  ●  ● │   capacity = 60 (max burst)
        │ ●  ●  ●  ●    │   refill_per_sec = 1 (sustained = 60/min)
        └───────────────┘

Each request → −1 token
Time passes  → +1 token/sec, capped at 60
Bucket empty → 429 Too Many Requests
```

| Property | Why it matters |
|----------|----------------|
| Allows bursts | Smooth user experience: user can fire 60 fast, then must wait |
| Smooth refill | No "boundary spike" issue you get with fixed windows |
| Per-key | One noisy customer doesn't starve another |
| Atomic ops | Two concurrent requests can't both think there's "1 token left" |

**Used by:** AWS API Gateway, Cloudflare, Stripe, GitHub. Industry-standard.

---

### 🎓 Why Redis?

Multi-process. If you run uvicorn with 4 worker processes, each in-memory bucket would be a separate counter — attackers could send 60 to each = 240 total before any of them said no.

Redis is **shared state**: every worker checks the same counter atomically. The Lua script makes it atomic so even concurrent reads-and-writes are safe.

**Why fall back to in-memory?** Single-process dev environments don't need Redis. Graceful degrade matches the W3 pattern (Groq-key-missing degrades L2). Same code, two implementations.

---

### 🎓 Lua scripts in Redis = atomic transactions

Naive Python:
```python
tokens = redis.get(key)        # read
if tokens >= 1:
    redis.set(key, tokens - 1)  # write
```
Race condition: two requests both read `tokens=1`, both decrement, both pass. Bug.

Atomic Lua:
```lua
local tokens = redis.call('HMGET', key, 'tokens')
if tokens >= 1 then
  tokens = tokens - 1
end
redis.call('HMSET', key, 'tokens', tokens)
```
Lua runs **inside the Redis server**, no network round-trip in the middle, no race. This is the standard pattern.

---

### 🎓 FastAPI middleware vs dependency

We chose **dependency** (`Depends(enforce_rate_limit)`) over **middleware** because:

- Dependencies can return rich `429` JSON with `Retry-After` headers
- Dependencies only run on the routes that opt in
- Dependencies show up in OpenAPI docs (auto-documented)
- Middleware runs on every request including `/health` (we don't want /health rate-limited)

---

### 🎓 The two bugs the new tests caught

**Bug 1 — lifespan timeout in tests.** Loading L1a + L1b + L2 + Redis ping took >5 s. asgi-lifespan's default 5 s startup window killed the app before it finished booting. Fix: `LifespanManager(app, startup_timeout=60.0)`.

**Bug 2 — division by zero.** When `refill_per_sec=0` and the bucket is empty, computing `retry_after = 1 / refill_per_sec` divides by zero. Fix: `if refill_per_sec > 0 else float("inf")`.

Lesson: **unit tests on edge cases catch math bugs you don't otherwise see**. We never use `refill=0` in production, but exercising it forced us to handle it cleanly.

## 6. Tools used in W7 — quick reference

| Tool | Role | Why this one |
|------|------|---------------|
| **Ollama** | Self-hosted LLM runtime | One-line install, OpenAI-compat API, runs CPU-only |
| **`llama3.2:3b`** | The actual local model | 2 GB, fast on CPU, decent quality |
| **`openai` SDK** | Used for Ollama too | Same code path as Groq L2 — provider-agnostic |
| **Redis** | Shared rate-limit counter | Standard, atomic, persistent |
| **`redis.asyncio`** | Async Redis client | Doesn't block FastAPI's event loop |
| **Lua scripts** | Atomic check-and-consume | Standard token-bucket pattern in Redis |
| **`asgi-lifespan`** | Fires lifespan in tests | We bumped its startup_timeout to 60 s |

### Why **NOT**

- ❌ Token bucket via fixed-window counters — boundary spikes (user fires 120 in last+next second windows)
- ❌ Sliding window log — memory cost grows with traffic
- ❌ Per-IP rate limiting — easy to bypass with proxies; per-key is the right granularity for an authenticated API
- ❌ Local LLM via raw `requests` — `openai` SDK gives us the OpenAI-compat URL for free
- ❌ FastAPI middleware (instead of dependency) — too coarse, hits `/health` too

## 8. What we did NOT do (and why)

| Skipped | Why |
|---------|-----|
| Per-key cost ceiling (daily $$ cap) | Token-bucket already covers DoS; a separate cost cap is W8 work if we go production |
| Per-IP rate limit | Authenticated API — per-key is the right unit |
| GPU acceleration for Ollama | Optional polish — CPU is enough to demo |
| Switch L2 from Groq to local Llama | Could have, but Groq is much faster (300 ms vs 5 s); Ollama is the *backend* (user-visible LLM), not the L2 judge |
| Distributed rate-limit (multiple Redis nodes) | Single Redis is plenty for portfolio; cluster comes later |
| Streaming responses (SSE) for Ollama | Adds complexity, not in scope; output filter would also need streaming-aware logic |
